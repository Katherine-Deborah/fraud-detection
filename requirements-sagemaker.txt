# Session 6: SageMaker training job -- isolated environment.
#
# mlflow==2.12.2 (numpy<2, pyarrow<16) and sagemaker==2.232.2 (numpy<2.0)
# both hard-pin pre-2.0 numpy, incompatible with feast==0.65.0's
# numpy>=2.0/pyarrow>=16.1 requirement in the main requirements.txt.
# Installing these two files into the SAME venv breaks feast. Use a
# separate venv for the Session 6 scripts (training/sagemaker_*.py,
# training/register_sagemaker_model.py):
#
#   python -m venv .venv-sagemaker
#   .venv-sagemaker/Scripts/pip install -r requirements-sagemaker.txt
#
# This venv never touches Kafka/Feast/Airflow code, only S3/SageMaker/MLflow
# calls and local model (de)serialization, so the older numpy/pyarrow here
# are harmless -- confirmed no runtime conflict for what these scripts do.
#
# scikit-learn is pinned to 1.2.1 to exactly match sagemaker_launch.py's
# framework_version="1.2-1" container -- NOT for API compatibility (that's
# stable across versions) but because scikit-learn 1.3 changed the pickled
# tree-node binary layout, so a model trained in the 1.2.1 container can't
# be joblib.load()ed under a newer scikit-learn. mlflow-skinny is pinned
# alongside mlflow to the same version -- letting pip resolve it
# independently pulled in a newer mlflow-skinny transitively (likely via
# sagemaker's own sagemaker-mlflow extra), which then made mlflow.sklearn
# calls target a newer REST API the pinned mlflow==2.12.2 tracking server
# doesn't have. If reinstalling this venv from scratch, install
# mlflow/mlflow-skinny first, scikit-learn last -- installing mlflow after
# scikit-learn silently upgrades scikit-learn again since neither mlflow
# package pins it. See docs/sagemaker.md for the full story.
