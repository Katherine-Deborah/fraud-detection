# Real-Time Serving — Session 8

A FastAPI gateway backed by Triton Inference Server, scoring transactions
in real time using the current MLflow-registry **production** model
(Session 7: Random Forest, v2) exported to ONNX. Per PROJECT.md §5.7: the
gateway pulls behavioral features from the Feast/Redis online store by
`account_id`, not from the request payload.

## Architecture

```
client -> FastAPI gateway (serving/app.py, local process, port 8090)
             |-- get_online_features(account_id) --> Feast -> Redis (online store, db 0)
             |-- build 29-column feature vector
             |-- POST /v2/models/fraud_rf/infer --> Triton (docker, port 8000)
             <-- fraud_score, is_fraud, threshold, ...
```

Only the production model is served (confirmed with the user for this
session's scope: production-only, not all 4 model types) -- if a future
session promotes a different algorithm to production, re-running the
export pipeline below picks that up automatically.

## ONNX export pipeline

Two scripts, run in sequence, **in separate processes**:

```bash
.venv-registry/Scripts/python training/fetch_production_model.py   # mlflow only
.venv-registry/Scripts/python training/export_to_onnx.py            # onnx/skl2onnx only, no mlflow
```

They're split because `import mlflow` followed by
`from skl2onnx import convert_sklearn` **segfaults** (STATUS_ACCESS_VIOLATION)
in the same process on this machine -- reproduced down to just those two
imports with nothing else in between, independent of any of this
project's own code. Almost certainly a native protobuf descriptor-pool
conflict between mlflow's and onnx's bundled generated proto code. Workaround:
`fetch_production_model.py` loads the model via mlflow and dumps it to
`serving/_export_staging/model.joblib` (gitignored, regenerated by
running the script); `export_to_onnx.py` loads that joblib file and never
imports mlflow.

`export_to_onnx.py` also:
- Converts with `skl2onnx.convert_sklearn(..., options={id(model): {"zipmap": False}})`
  so the ONNX graph outputs a plain `[N, 2]` float probability tensor
  instead of a list-of-dicts (Triton's ONNX Runtime backend needs a plain
  tensor).
- Sanity-checks the conversion: runs both sklearn's `predict_proba` and
  onnxruntime on the same 500 sampled training rows and asserts the max
  absolute probability difference is under `1e-4`. **Actual measured
  diff: `6.45e-08`** -- the ONNX graph is numerically equivalent to the
  original sklearn model, not just structurally similar.
- Generates `serving/triton_model_repo/fraud_rf/config.pbtxt` from the
  *actual* ONNX graph's I/O names/shapes (`float_input` / `probabilities`)
  rather than hand-typing them, so the config can't silently drift out of
  sync with what skl2onnx produced.
- Writes `serving/model_metadata.json` -- everything `serving/app.py`
  needs at request time (feature column order, sentinel fill values,
  category list, decision threshold, model version) without importing
  mlflow or scikit-learn.

`requirements-registry.txt` gained `skl2onnx==1.20.0`, `onnx==1.22.0`,
`onnxruntime==1.18.1` (not the latest 1.28.0 -- that version fails to
import on this machine with "DLL load failed while importing
onnxruntime_pybind11_state", likely a VC++ runtime baseline mismatch;
1.18.1 imports cleanly and is more than sufficient for a
RandomForestClassifier graph).

Added to `docker-compose.yml` as `triton`

## FastAPI gateway (`serving/app.py`)

### Design decision: read-only against Feast

`/predict` calls `store.get_online_features()` — **read-only**. It does
**not** call `feature_store.online_features.OnlineFeatureEngine.compute()`,
which would recompute features against the incoming transaction and
mutate the account's rolling Redis state as a side effect. This was
confirmed with the user before building:

1. `docs/feature_store.md` already documents that the online engine's
   Redis updates are **not idempotent**. A load test hammering a mutating
   endpoint would inflate rolling counters and corrupt the same account
   history that future requests (including the *next* load test run)
   read from. A read-only endpoint can be hit repeatedly with zero side
   effects — which is exactly what this session's load test needed.
2. A scoring request isn't necessarily a confirmed real transaction (a
   pre-auth check, a what-if query). State advancement stays exclusively
   owned by the Kafka consumer → `OnlineFeatureEngine` → Feast push
   pipeline (Sessions 2/3) — one source of truth for "what actually
   happened."

**The real tradeoff, stated plainly:** fetched features reflect the
account's state as of its *last materialized/pushed* transaction, not
freshly recomputed against the transaction being scored right now.
`txn_count_last_1h/24h` won't include the current request;
`amount_to_avg_ratio` reflects the previous transaction's ratio, not this
one's. This is correct for the intended real-time use case (scoring an
account's *next* transaction as it happens, using its most recently known
profile) but will look wrong if you replay an arbitrary *historical*
mid-sequence transaction out of order — verified directly: scoring one of
`acct_020744`'s real fraud transactions (seq 375 of 495) using the
account's Feast-materialized snapshot (which reflects seq 495, a later
and unrelated benign transaction) returns a low score (0.074, correctly
non-fraud *for that stale context*, but not a meaningful test of the
fraud transaction itself). This is a testing artifact, not a serving bug.

`hour_of_day`/`day_of_week`/`is_weekend` are the one exception: they're
pure functions of the transaction's own timestamp, not history, so the
gateway computes them fresh from the request instead of pulling
(possibly stale) values out of Feast.

### Cold-start accounts

If `get_online_features` returns no row for `account_id` (never
materialized or streamed), the gateway falls back to the same
first-transaction defaults `OnlineFeatureEngine` uses (all counts reset
to 1, `is_new_device`/`is_new_merchant_category` = 1, sentinel -1 for
time/geo-since-last). One known gap: `home_distance_km` can't be computed
without the account's home coordinates (only `OnlineFeatureEngine` loads
`data/raw/accounts.parquet` for that), so it falls back to `-1`, which is
mildly out-of-training-distribution for that specific field (offline
training data always has a real `home_distance_km`). Narrow, rare edge
case (the 50,000 known synthetic accounts cover the realistic demo/load-test
path) — a fuller fix would load the accounts table in the gateway too;
not done here as it's genuinely rare, not a quality-affecting gap for the
common path.

### Minimal request schema

`PredictRequest` is narrower than the raw Kafka message shape
(`consumer/consume.py`'s `REQUIRED_FIELDS`): `device_id` and `location`
are dropped rather than accepted-and-silently-ignored, since neither
currently feeds the read-only feature vector. An honest API surface only
accepts fields that actually affect the score.

### Sync `requests` over `httpx.AsyncClient` (measured, not assumed)

Both the Feast call and the Triton call are dispatched via FastAPI's
`run_in_threadpool`, using plain `requests` for Triton rather than an
async `httpx.AsyncClient`. This was a direct, measured finding, not a
default choice — see "Load test" below for the numbers that drove it.

## Load test

Command: `.venv-serving/Scripts/locust -f serving/locustfile.py --headless -u <N> -r <rate> -t <duration> --host http://localhost:8090`

The gateway ran with `uvicorn --workers 4` (all other services — Triton,
Redis, MLflow — in Docker, unmodified from their normal config). Real
measured numbers, not placeholders:

| Concurrent users | Requests | Failures | RPS | p50 | p95 | p99 | max |
|---|---|---|---|---|---|---|---|
| 5 | 1,040 | 0 | 35.4 | 120ms | 170ms | 240ms | 2,200ms |
| 50 | 1,772 | 0 | 60.6 | 490ms | 2,700ms | 4,200ms | 6,600ms |
| 100 | 2,728 | 0 | 45.8 | 1,600ms | 5,400ms | 8,300ms | 11,800ms |

**This misses PROJECT.md's target (p99 < 50ms @ 500 TPS) by a wide
margin, reported honestly per that section's own instruction to report
the real number even if it misses.** Zero request failures at every
concurrency level — the system stays correct under load, it just isn't
fast enough yet.

### Root-cause investigation (not just "it's slow")

Isolated each hop with direct benchmarks (200 requests, 50-way thread
concurrency) to find where the time actually goes, rather than guessing:

| Component tested in isolation | Method | RPS | p50 | p99 |
|---|---|---|---|---|
| Triton `/infer`, via `httpx.AsyncClient` (asyncio) | direct | 131.2 | 349ms | 435ms |
| Triton `/infer`, via `requests` + `ThreadPoolExecutor` | direct | **444.5** | **54ms** | **145ms** |
| `GET /health` (no-op endpoint) through the full gateway/uvicorn stack | Locust, 50 users | 955.0 | 26ms | 56ms |
| Feast `get_online_features`, via `requests`-style sync call + `ThreadPoolExecutor` | direct | 195.7 | 3.7ms | **992ms** |

Findings, in order of discovery:

1. **`httpx.AsyncClient` over Windows' default asyncio event loop
   (`ProactorEventLoop` — uvicorn can't use `uvloop` on Windows) has real
   overhead under concurrent sockets.** The identical Triton call is
   ~3.4x faster in RPS and ~3x lower p99 through a synchronous
   `requests.Session` + thread pool than through `httpx.AsyncClient`.
   This is why `serving/app.py` uses `requests` for the Triton call, not
   `httpx` (see design decision above) — this fix is in the shipped code.
2. **The gateway's own connection-accept path is not the bottleneck.** A
   trivial `/health` endpoint sustains ~955 req/s at 50 concurrent users
   through the exact same uvicorn/Windows stack — ruling out "uvicorn
   itself can't handle concurrent connections on Windows" as the
   explanation for `/predict`'s slowness.
3. **The dominant, *unresolved* bottleneck is Feast's Python client under
   thread concurrency**, not Triton and not the gateway's own
   request-handling. p50 for a single `get_online_features` call is fast
   (3.7ms — consistent with a direct Redis hash read), but p99 balloons to
   ~1000ms once 50 threads are calling it concurrently, a >250x gap
   between typical and tail latency that Triton's own concurrent
   benchmark doesn't show at the same concurrency level. This points at
   contention inside Feast's `FeatureStore`/`RedisOnlineStore`
   implementation (registry access, provider construction, or connection-pool
   checkout) rather than Redis itself, though the exact internal cause
   wasn't traced further — see below.

Applying the `requests`-over-`httpx` fix for the Triton leg (finding 1)
did **not** meaningfully improve the end-to-end `/predict` numbers in the
table above, which is expected once finding 3 is understood: Feast's
client, not the Triton call, is the dominant cost under concurrency.

## What I'd try with more time

- Trace the Feast/Redis tail-latency growth further — likely candidates:
  the `RedisOnlineStore`'s connection-pool sizing (Feast doesn't expose a
  documented way to size it), or Python-level locking inside
  `FeatureStore.get_online_features` around registry/provider access. If
  it's connection-pool starvation, sizing the pool explicitly would be a
  quick fix; if it's a GIL-bound critical section inside Feast itself,
  the real fix is bypassing Feast's Python client for the serving hot
  path and reading the same Redis hash keys directly (the online store's
  key format is already documented in `feature_store/online_features.py`),
  matching a common production pattern of "Feast for offline/materialization,
  a thin custom client for the serving hot path."
- Re-measure on Linux (Session 10's eventual deployment target). Two of
  the three findings above are plausibly Windows-specific
  (`ProactorEventLoop` overhead, and possibly some of Feast's contention
  too) — the numbers in this doc are honest for *this dev machine*, not
  necessarily representative of where this would actually run in
  production.
- If Feast's tail latency turns out to be irreducible, consider a small
  in-process LRU cache in the gateway (account_id → last-fetched feature
  row, short TTL) to absorb repeated lookups for the same account within
  a burst — trades a bit of extra staleness (already a documented
  tradeoff of the read-only design) for materially lower p99.
- A real Grafana/Prometheus view of gateway + Triton latency (Session 9)
  would make this kind of bottleneck-hunting visible without ad hoc
  benchmark scripts.

## Running it yourself

```bash
# 1. Export the production model (once per production-model change)
.venv-registry/Scripts/python training/fetch_production_model.py
.venv-registry/Scripts/python training/export_to_onnx.py

# 2. Bring up Triton + Redis
docker compose up -d redis triton

# 3. Run the gateway (local process, not containerized -- see docker-compose.yml)
python -m venv .venv-serving
.venv-serving/Scripts/pip install -r requirements-serving.txt
.venv-serving/Scripts/python -m uvicorn serving.app:app --host 0.0.0.0 --port 8090 --workers 4

# 4. Score a transaction
curl -X POST http://localhost:8090/predict -H "Content-Type: application/json" \
  -d '{"account_id":"acct_000000","amount":123.45,"merchant_category":"electronics"}'

# 5. Load test
.venv-serving/Scripts/locust -f serving/locustfile.py --headless \
  -u 100 -r 20 -t 60s --host http://localhost:8090 --csv=docs/eda/load_test
```

Raw Locust output for the runs in this doc: `docs/eda/load_test_stats.csv`
(100 users) and `docs/eda/load_test_low_concurrency_stats.csv` (5 users).

## Environment notes

- `training/fetch_production_model.py` / `training/export_to_onnx.py` run
  under `.venv-registry` (reused from Session 7, extended with
  skl2onnx/onnx/onnxruntime — see requirements-registry.txt).
- `serving/app.py` / `serving/locustfile.py` run under a new isolated
  `.venv-serving` (requirements-serving.txt) — same root cause as every
  other isolated venv in this project: feast needs numpy>=2, mlflow needs
  numpy<2. The gateway never imports mlflow/sklearn at request time, so
  there's no reason to fight that resolver conflict here either.
